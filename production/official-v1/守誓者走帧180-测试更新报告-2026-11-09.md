## 0. 结论先行

**四门禁恢复全绿，用例数 122 文件 / 1562 用例（原 122 / 1561，+1 条新增语义用例）。**

**5 处红的根因不是"期望帧名算错"，而是测试的推进节奏（110ms/帧）是按 330 定制的**——`110 × 3 = 330 = 整周期`。
帧长改 180 后 110ms 不再整除 180，于是"推进 3 帧后应到下一档"这句断言**本身失去了语义**（不是期望值错了，是取样网格错了）。
所以修法是**换取样网格（110ms → 60ms，3 帧 = 180ms = 恰好一个帧长），而不是逐个改期望帧名去凑**——
后者会把"整周期边界"这个真正被测的语义悄悄丢掉，是另一种形式的放宽。

- 逐处判定：**3 处属「时序」语义（保留精确断言，只重算推进节奏）／1 处属「时序（setup）」／1 处属「调用次数效率」语义／1 处属「常量规格」**（明细见 §1）。
- **没有任何一处退化成 `toBeGreaterThan` / `toBeDefined` / `toBeTruthy`**；全是 `toBe` 精确值（唯一非 `toBe` 是既有的 `toBeCloseTo`，未动）。
- **无"该改实现而非测试"的疑点**（§5 给论证），实现逻辑一行未动。
- 另**新增 1 条帧长无关的帧序用例**：把"单调前进 / 不回头 / 不跳档"独立钉住，避免下次调帧长时同一批用例又整片变红。

## 1. 五处逐条：原文 → 改后 → 语义判定

### ① L209（旧行号）`toBe('...walk-c')` —— 判定：**时序**

| | |
|---|---|
| 原文 | `pump(h, 3, 0.11, 6); // 660ms` → `expect(frame.name).toBe('summon-oathkeeper-walk-c')` |
| 改后 | `pump(h, 3, 0.06, 6); // 360ms → 2 个帧长 → c` → `expect(frame.name).toBe('summon-oathkeeper-walk-c')`（新 L218） |

**理由（为什么判"时序"而不是"实现细节钉死"）**：这条用例的标题就是"起步第一帧 = walk-a；移动态帧序 a→b→c→d→a"，
断言的是**"累计 t 毫秒 → 第 `floor(t / 帧长)` 档"这个规格映射**，帧长是被裁定的规格值（180）。它不是在断言"第 3 次
`update()` 后恰好是 c"（那才是实现细节）——证据是：原用例刻意选了 `3 × 110ms = 330ms` 这个**整周期点**，
说明作者要验的是"整周期处换档"，而非"某次调用的结果"。

**改法**：保持被测语义（整周期对齐）不变，把推进节奏换成能整除 180 的 60ms，四档边界逐一精确断言。
新节奏下的累加器实迹（模型复算，与实现 `Math.floor(walkElapsedMs / WALK_FRAME_MS) % 4` 一致）：
`a(0) → b(180) → c(360) → d(540) → a(720)`。

### ② L224（旧）`toBe('...walk-a')` —— 判定：**时序边界**

| | |
|---|---|
| 原文 | `330ms 边界双向：329ms 仍是 a，330ms 进 b`：`pump(1, 0.329)` → a；`pump(1, 0.001)` → b |
| 改后 | `180ms 边界双向：179ms 仍是 a，180ms 进 b`：`pump(1, 0.179, 6)` → a；`pump(1, 0.001, 1)` → b（新 L248-258） |

**理由**：这是最典型的时序规格断言——"差 1ms 不换档、到点才换档"，正是 `floor()` 边界的双向测（纪律 2）。
只要帧长是 180，这段就**严格等价**于原来的写法；改的是数值，不是强度。

> 顺带一个副产品：见 §4，**这一条单独就能把帧长唯一地钉死在 `(179, 180]` ≡ 180**。

### ③ L233（旧）`toBe('...walk-c')` —— 判定：**时序（且是 setup，非被测行为）**

| | |
|---|---|
| 原文 | `pump(h, 7, 0.11, 6); // 走到 c` → `expect(...).toBe('...walk-c')` |
| 改后 | `// setup（非被测行为）：60ms/帧 × 7 = 360ms = 第 3 档` `pump(h, 7, 0.06, 6)` → `toBe('...walk-c')`（新 L263） |

**理由**：本用例真正的被测行为是**"停下后累加器归零 → 再起步必从 a 帧"**（防"崴脚"，方案 §3.2）；
`走到 c` 只是把状态推到"循环中段"的前置摆设。它红的原因是 `7 × 110 = 660ms` 在 180 下已是第 4 档 d。
**没有降级成"只要不是 a 即可"**：仍精确断言 `walk-c`，只把节奏换回 60ms（`7 × 60 = 360ms → c`），
并加注释明示"这段是 setup"，免得后人再把它当成被测结论去调。

### ④ L246（旧）`expect(textureSets).toBe(1)` —— 判定：**调用次数（效率）语义**

| | |
|---|---|
| 原文 | `pump(h, 3, 0.11, 6); // a × 4 帧，帧不变` → `toBe(1)`；`pump(1, 0.11)` → `toBe(2)` |
| 改后 | `pump(h, 3, 0.06, 6); // 3 × 60ms = 120ms < 180ms → 同一个 a 帧` → `toBe(1)`；`pump(1, 0.06)` → `toBe(2)`（新 L275-279） |

**理由**：这条断的是"**换帧才 `setTexture`，不每帧刷**"（热路径纪律：帧不变不重设纹理、不重算缩放）。
原注释"a × 4 帧"其实已经写错了（3 次 `pump` + 首帧 = 4 次 update，`110 × 300` 里 330 恰好是周期边界，所以前 3 帧确实都在 a）。
180 下 `3 × 110 = 330 > 180`，第 3 帧就换到 b → 2 次，于是红。
**改法保住被测性质**：把 3 次 update 压进同一个帧保持窗口（120ms < 180ms）→ `toBe(1)`；再 1 帧跨过 180 → `toBe(2)`。
若实现退化成"每帧都 `setTexture`"，会得到 `3 / 4` → 仍然失败。

### ⑤ L479（旧）`expect(WALK_FRAME_MS).toBe(330)` —— 判定：**常量规格**

| | |
|---|---|
| 原文 | `expect(WALK_FRAME_MS).toBe(330);`（用例名"常量钉死：330ms/帧…"） |
| 改后 | `expect(WALK_FRAME_MS).toBe(180);` + 6 行裁定依据注释（新 L509-516） |

**注释里落的依据**（取自 A/B 报告 §0/§2，非我新造数）：
- 滑步比 = `120px/s × 帧长 ÷ 美术每帧位移 12.44px` → **330ms = 3.18（>1.8 阈值，FAIL）／180ms = 1.74（CONCERNS 带内）**；
- 每姿势位移 ÷ 内容宽 78px：**0.51 → 0.28**；
- 一圈 **1320ms → 720ms**，对成人步行循环 0.8~1.0s 由"偏慢"变为"偏快 10~28%"。

### ⑥ 新增 1 条（36 → 37 用例，非 red 项，属加固）

`帧序语义（帧长无关）：连续 update 期间 a→b→c→d 单调前进，不回头、不跳档`（新 L230-246）：
`dt = 110ms < 帧长` → 单帧最多推进一档；连推 24 帧，逐帧检查 `Δindex ∈ {0, 1} (mod 4)`（0 = 本帧未换帧，正常；
2/3 = 跳档/倒退，失败），并要求 24 帧内走满 4 档、全程不掉回 idle。
这条**不依赖帧长具体数值**（只要求 `dt < 帧长`），是"帧序"这一语义的兜底——下次再调帧长，这条仍应绿，
从而把"红了是因为节奏取样错了"和"红了是因为帧序真坏了"区分开。

## 4. 断言强度自查：会不会"为了过而糊过去"

没有用任何模糊断言替代精确断言。为了**客观**证明这一点（而不是只看"绿了"），我把四类用例的断言逻辑参数化，
**穷举帧长 P = 80..360（步长 5）** 复算"每条用例在 P 下会不会红"（模型与实现同式：`floor(accum / P) % 4`，
进入 move 的那一帧把 accum 归零）：

```
P=180: T1 ✓ T2 ✓ T3 ✓ T4 ✓ T5 ✓        ← 唯一 5/5 全绿
P≠180 中能过 ≥3 条的只有：P=145,150,155,160,165,170,175 —— 均只过 [T1, T3, T4]
（其余 P 连 3 条都过不了）
```

两条读数：

1. **`P = 150` 会骗过用例①②③④里的三条**——因为 `180/150 = 1.2`，60ms 网格下四档的**落点档位与 180 相同**。
   这正是"只改期望帧名去凑"的危险之处：单看 T1/T3/T4 变绿，会以为"帧长没问题"。
2. **但没有任何 `P ≠ 180` 能全绿**：边界用例 T2 要求 `179 → a` 且 `180 → b`，等价于 `179 < P ≤ 180`，
   配合整数帧长 → **P ≡ 180**；再加 T5 的 `toBe(180)` 双保险。**所以"180"这个规格仍被唯一钉死，没有松动。**

（新增的帧序用例不在此穷举里——它按设计就与 P 无关，只要求 `dt < P`；这是刻意的，见 §1⑥。）

## 5. 「该改实现而非测试」的疑点核查

**结论：没有。5 处红全部由"测试侧采样网格按 330 定制"造成，实现侧不背这个债。**

论证：实现里与帧长相关的只有一行 `Math.floor(this.walkElapsedMs / WALK_FRAME_MS) % 4`（`oathkeeper-view-sprite.ts:323`），
它的正确性要件是——(a) 只有连续 move 才累加、离开 move 归零；(b) 进入 move 的那一帧不累加（从 a 起步）；
(c) 用 `floor` 而非 `round`（回退时不"跳过早该显示的一帧"）。这三条与帧长取值**正交**，180 与 330 同样成立；
本次 37 条用例在 180 下全绿，即这三条仍被覆盖。**故不动实现。**
