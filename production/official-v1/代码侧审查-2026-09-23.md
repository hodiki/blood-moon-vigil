**一句话定性**：这是一份**架构收口良好、但"通关语义"存在一条已存在的 P0 错误行为、且质量门缺一条能拦住该类缺陷的防线**的冻结仓库——血月化身（`boss_4`）击杀会直接触发胜利终局，与设计「稀有奖励 Boss 不阻塞通关」相悖。

### 2.1 P0（#1）影响面细化 —— 血月化身击杀触发通关

**调用链（文件:行级）**
1. `tickAvatarTrigger()`：`elapsedSeconds ∈ [270,360)` 且 1s 节拍且 `moonAvatarTriggerDue(t, random)` 命中 → `spawnAvatar()`（`PlayScene.ts:1037-1047`）。
2. `spawnAvatar()`：`enemyPool.acquire(...)` + `avatar.spawnByBossConfig(BOSSES.boss_4, bx, by)`（`PlayScene.ts:1050-1058`）→ `kind='boss'`、`enemyId=null`（`enemy.ts:263-266`）。

4. `onBossDefeated()`（**唯一** `finishGame(true)` 入口，`PlayScene.ts:878-899`）→ `finishGame(true)`（`PlayScene.ts:902-949`）。

**出现概率（②）**：窗口 `[AFTER_SECONDS=270, BOSS_TIME_GATE=360)`（`PlayScene.ts:98-99,1037-1040`），1s/次 × `TRIGGER_CHANCE=0.05`（`enemies.ts:300-308`）。窗口约 90 次判定，触发概率 ≈ `1 − 0.95⁹⁰ ≈ 99.0%`。即**凡存活过 4:30 的局，几乎必然进入化身并（若击杀）通关**；AI 测试实测 `t=276.4` 即触发（`...ai-auto-test.md:220`），与概率吻合。

### 2.3 F3（#6）pivot 风险判定细化

- 设计侧在 `pivots.json:note` 明确**刻意不写入 TexturePacker 的 `frames[].pivot`**（避免 Phaser 自动 `setOrigin`），改由"引擎接入时与碰撞圆心做 offset"——即 pivots 是**待引擎代码消费**的交付物，当前**零消费**。
- 混尺寸事实：`combat-display-scale.ts:1-12` 将 64 帧抬到 128（`scale=128/frameW`）、128 帧 1:1、守誓者 192 帧 1:1。因显示尺寸被归一化到同一世界边，且各帧归一化 pivot 值彼此接近（`player≈0.9297`、`gravekeeper≈0.9427`、`boss≈0.9473`，见 `pivots.json`），**跨尺寸脚底错位理论量级 ≈ (0.947−0.930)×128 ≈ 2px**——量级很小。
- 因此判定：**"脚底严重不齐"证据不足**；更准确的残留是——① 每个实体的**碰撞圆心 = 贴图中心**（`body.setCircle` 于默认原点，`player.ts:48`、`enemy.ts:197`），而非脚底/地面点，设计注中的"碰撞圆心 offset"未实现；② 逐帧 pivot 完全未参与，任何 pivot 偏离更大的新帧会**线性放大**该偏差。
- **结论**：F3 = 已产出未接线交付物，**实际可见风险低-中，需真机截图标定方可定档**；不宜按"已坏"处理，但应登记为技术债并在接线新帧前处理。

**建议方案（成本 / 收益）**

| 项 | 内容 |
|---|---|
| 新增 script | `"test:e2e": "playwright test"`（或 `"smoke": "npm run build && playwright test"`）——不改现有 scripts |

| `bucketEquiv()` 只按基础 id 折算、漏计 `_2` 第二铺位节点 | **成立** | `tree-state.ts:231-241`（查表键 vs `node.id`，见补-3） |
| 现有断言给出**假 PASS**（伤害 5.0% / 生存 3.4% / 合成 8.4%） | **成立**（复算吻合） | 复算 `damage=5.00% survival=3.40% combined=8.40% PASS=true` |
| 按**全属性层（含 `_2`）**实算 = 合成 **10.7% > ≤10% 红线**（+0.7pp） | **成立**（按现系数锚 + 「合成=d+s」口径；口径本身存疑，见补-2/补-4） | 复算 `damage=6.60% survival=4.10% combined=10.70% over10=true` |

**一句话定谳**：**这颗假 PASS 是真的**——但它**只坏在「校验/配置守护」层，运行时数值是对的**（`bucketEquiv` 与开局数值路径无交集）。故 A-13 的 P0 应**限定为「门禁层 P0」**，与主表 #1（化身通关，**运行时行为 P0**）不同类。

## 补-2 真相口径：正确三桶实算值 + 「合成」分母

| 桶 | 现断言读数（漏 `_2`） | **全层实算（含 `_2`）** | 红线 | 结论 |
|---|---|---|---|---|
| 伤害类 | 5.0% | **6.6%** | ≤8% | PASS |
| 生存类 | 3.4% | **4.1%** | ≤6% | PASS |
| 合成 | 8.4% | **10.7%** | ≤10% | **FAIL（越线 +0.7pp）** |

**逐节点分解（系数取自 `TALENT_BUCKET_EQUIV`，`talent-tree.ts:60-65`；×`maxPurchases`）**

- 伤害桶 = `a_attack 0.4×2=0.8` + **`a_attack_2 0.4×1=0.4`** + `a_damage 1.2×2=2.4` + **`a_damage_2 1.2×1=1.2`** + `a_attack_speed 0.5×2=1.0` + `a_cooldown 0.4×2=0.8` → **6.6**
- 生存桶 = `a_life 0.7×2=1.4` + **`a_life_2 0.7×1=0.7`** + `a_move_speed 0.5×2=1.0` + `a_heal_efficiency 0.5×2=1.0` → **4.1**
- （加粗三项 = 漏计的 `_2` 节点；合计漏计 1.6 + 0.7 = **2.3pp**，正是 8.4%→10.7% 的差）

**「合成总量」的分母口径（回答任务 3）**

- **不是节点数占比，也不是层级权重。** 三桶是**强度等效百分比**：伤害桶 = **DPS 等效 %**，生存桶 = **承伤等效 %**（GDD §3.6 `gdd-talent-tree.md:85-90` / §6.1 `:215-222`）。系数表按「每层等效 %」建，断言乘 `maxPurchases` 求和 = 全满等效。
- **配置实现**：`合成 = 伤害等效 + 生存等效`（`tree-state.ts:257` 的 `d + s <= TALENT_REDLINE.combined`）。
- **GDD 语义**：§3.6/:89「合成对成型强度影响 ≤10%」、§6.1/:221 分母写「对 **6min 成型强度**」——**未给可计算定义式**，与「两个等效 % 直接相加」**并不等价**。且 GDD §6.1 自身给「伤害 ≈7~8% + 生存 ≈5~6%」之和 = **12~14% > 10%**（文档内自相矛盾，即设计侧 B-1）。
- **结论**：「合成 10.7% 越线」在**现系数锚 + config 的 `d+s` 口径**下成立；若系数被模拟批次重标、或「合成」改按独立「6min 成型模拟影响」口径，越线值随动。**这条不是设计绝对值，是「按现行配置口径的成绩单」。**

## 补-3 假 PASS 机制（一句话）

**遍历是完整的，丢的是系数查表**：`bucketEquiv` 的 `for (const node of TALENT_TREE)` 覆盖全部节点、`node.bucket === bucket` 过滤也对；但 `TALENT_BUCKET_EQUIV` **只按基础 id 建键**（`a_attack/a_damage/a_attack_speed/a_cooldown/a_life/a_move_speed/a_heal_efficiency`），而第二铺位是**独立 id**（`a_attack_2/a_damage_2/a_life_2`），`table[node.id]` 对 `_2` 返回 `undefined`，被 `if (per)` 静默吞掉 → `_2` 贡献 0。**是「id 归一化/键失配」，不是「遍历只覆盖一铺位」**（`tree-state.ts:237-238`）。

**为什么现有 `tests/unit/**` 没拦住（任务 3 的第二问）**

1. **自证（同义反复）**：唯一的红线用例 `tests/unit/progression/talent-tree-b5.test.ts:54-59` 断言的正是**同一个** `damageBucketEquiv() / survivalBucketEquiv() / allTreeBonusesWithinRedline()`——**拿被测函数当自己的 oracle**，只能测「值变没变」，测不出「公式对不对」。（对应 `trace_path(allTreeBonusesWithinRedline, inbound)` = 唯一调用者即该测试，运行时零消费。）
2. **缺覆盖型守卫**：没有任何用例断言「每个 `bucket ∈ {damage,survival}` 的属性节点，其 id（或归一化 id）必须在 `TALENT_BUCKET_EQUIV` 中有键」。该守卫缺失 → 「加了 `_2` 节点却没加系数键」的配置漂移无声通过。
3. **计数用例只管数量**：`:25`（15 属性节点）/ `:33`（12 支线）只测节点**个数**，不测「每个节点都被折算」。

## 补-4 影响面（最关键区分）：**只有校验/断言写错，实装是对的**

- **运行时数值路径不经过 `bucketEquiv`。** `trace_path(bucketEquiv, inbound)` 的调用者 = `allTreeBonusesWithinRedline` + `damageBucketEquiv` + `survivalBucketEquiv`（三者同文件 `tree-state.ts`）+ 测试；`allTreeBonusesWithinRedline` 的 inbound **仅测试 1 个**。即 `bucketEquiv` 家族是**纯断言/配置守护**，运行时零消费。
- **真实开局数值走 `computeTreeApplication → attributeDeltaOf`**（`tree-state.ts:188-213`），它**逐 `node.id` 直读 `node.machine × purchases`**，天然含 `_2`。只读复算实测：买 `{a_attack:2, a_attack_2:1, a_damage:2, a_damage_2:1, a_life:2, a_life_2:1}` → `attackFlat=6`（=2×2+2×1）、`damagePct=0.06`（=(2+1)×0.02）、`maxHp=45`（=(2+1)×15）→ **运行时含 `_2` = 真**。
- **消费点**：`src/scenes/PlayScene.ts:289` `computeTreeApplication(treeLedger, …)` → `:297` `treeApplier.applyToStats(treeApp)`。该链与 `bucketEquiv` **无交集**。
- **因此**：这颗假 PASS **不改变任何运行时数值**（不存在「实装漏算 → 玩家少拿到属性」或「实装越线 → 玩家数值超标」的情况）。它坏掉的是**「设计平衡红线」这张 CI/配置守护网**——真值（合成 10.7%）下红线本应告警，却报 PASS，**越线的 0.7pp 无人拦**。
- **严重度定性**：**门禁层 P0（红线守卫失效）**，**非**运行时 P0。

**同域补充发现（非 A-13 原命题，但同一函数）**：`bucketEquiv` **同时整体漏掉全部 12 个支线节点**——支线节点 `bucket` 字段为 `undefined`（复算：全表 bucket 分布 `{(none):23, damage:6, tempo:5, survival:4}`；`(none)=23` = 1 根 + 10 质变 + 12 支线），`node.bucket !== 'damage'` 直接 `continue`。而 GDD §4.3/:164 要求「**支线效果计入所属三桶折算**」。故三桶红线断言**同时漏计 `_2`（6 个）与全部支线（12 个）**——A-13 只点了 `_2` 半边，**支线半边未点**。→ 后续补键时需一并裁支线折算口径（哪些字段进伤害/生存桶）。
