## 3 · B2 `assets/raw/` 旧图退役（关窗动作）

| 文件 | 处置 | 理由 |
|---|---|---|
| `assets/raw/summon-oathkeeper.png` | → `assets/raw/_retired/summon-oathkeeper.png` | 旧 48 时代的 1024² 底图。契约升 192 后，任何人跑 `process.mjs summon-oathkeeper`（或任一 walk 帧 → `expandToFamilies` 把同族 raw 拉进来，或 `--all`）都会拿它**放大重采样覆盖新 192 帧**，且 `validate()` 只查尺寸会判 **PASS** |
| `assets/raw/summon-oathkeeper-v.png` | → `assets/raw/_retired/summon-oathkeeper-v.png` | 同上 |
| `assets/raw/summon-oathkeeper-tombstone.png` | **保留原位** | 墓碑契约仍是 48×48，且 192 墓碑图**尚未产出**。保留 raw 以便将来产出 192 墓碑时仍能走 `process.mjs --solo` |

- **方式**：`git mv` 移动到 `assets/raw/_retired/`（**不是删除**），文件名不变。
- **副作用（重要，已实测确认安全）**：`process.mjs` 的 raw 发现只有两条路径，**均为扁平、无递归**——
  - `listRawFrames()`（`process.mjs:310-316`）：`fs.readdirSync(RAW_DIR).filter(f => f.endsWith('.png'))`
  - `loadPrepared()`（`process.mjs:346`）：`path.join(RAW_DIR, frameName + '.png')`

  → 子目录 `_retired/` **不会被扫到**，所以退役生效；同时不必改名去骗 `isKnownFrame`。
- `assets/raw/` 下**无索引/清单文件**（`ls -a` 仅 `.`/`..`+ PNG），故无需同步其它清单。
- 已写 `assets/raw/_retired/README.md`：说明退役原因、保留项、残余风险与恢复方法。

### 3.1 关窗后的残余风险（低，已核）

| 场景 | 结果 |
|---|---|
| `process.mjs --all` | 守誓者族只剩 tombstone 一条 raw → 只会把 `frames/summon-oathkeeper-tombstone.png` 按 48 重写一遍（48→48）。**7 张 192 帧无 raw，不会被碰** |
| `process.mjs summon-oathkeeper` | 该帧报 `NO_RAW` 跳过；但 `expandToFamilies` 会把 tombstone 纳入并重写 48 墓碑（同尺寸）。**192 帧安全** |
| `process.mjs summon-oathkeeper-walk-b` | 同上：walk-b 自己 `NO_RAW`，只有 tombstone 会被碰。**192 帧安全** |

> 结论：**"旧 48 放大覆盖新 192"的路径已彻底掐断**。唯一仍可被重写的是 48 墓碑（尺寸不变，无损失）。

### 4.1 逐帧结果（原样）

**尺寸检查 8/8 全 PASS**（`192x192 == 192x192` ×7、`48x48 == 48x48` ×1）——即契约对齐正确。
3 个 FAIL **全部来自时间轴门禁**，非尺寸。

### 4.2 判定 A：48/192 **混档** —— 与方案 §75 预期一致（不算 bug，不要"修"）

`applyTemporalGates` 取族基帧 `summon-oathkeeper`（192 → `sizeBand` = 128 档）作为基准，
墓碑仍 48，两者指标在**不同像素空间**里比较：

| 成员 | hypot | 脚底 ΔY | 面积 Δ | 门限（tombstone 档 @128） | 判定 |
|---|---|---|---|---|---|
| `-v` | 0 | 0 | 0% | 4 / 0 / 15% | ✅ |
| `-walk-a` | 0.83 | 0 | 5.2% | 6 / 0 / 25% | ✅ |
| `-walk-b` | **8.29** | 0 | 6.6% | 6 / 0 / 25% | ❌ |
| `-walk-c` | 3.15 | 0 | 7.9% | 6 / 0 / 25% | ✅ |
| `-walk-d` | **7.78** | 0 | 2.2% | 6 / 0 / 25% | ❌ |
| `-tombstone` | **109.79** | **146** | **88.3%** | 12 / 1 / 25% | ❌ |

- **墓碑 FAIL 是"混档"的必然结果**：48px 帧与 192px 基准比重心/面积，数值必然爆表（109.8 / 146 / 88.3%）。
  **这是方案 §75 有意保留的已知状态**（192 墓碑图本批不存在），**不是回归、不要当 bug 修**。
  另外 `checkExisting` 已单独给墓碑算出正确度量（`footY=45`，`48x48` 尺寸 PASS），只是族口径拿它跟 192 基准比。
- ⚠ **顺手发现的真缺陷（混档的第 2 个后果，此前无人记录）**：
  `applyTemporalGates`（`process.mjs:513-518`）会把**基帧 pivot 无差别刷给族内所有成员**。
  于是 48 墓碑的 pivot 被 192 口径覆盖为 `y = 0.9974`（= 191.5/192），而它自己的实测值是
  `y = 0.9479`（= 45.5/48）。**差 0.0495 → 在 48px 上是 2.4px 下沉**，且 `pack.mjs` 会把这个值写进
  `assets/atlas/pivots.json`。
  本批已**手工还原** `report.json` 中墓碑 pivot 为其自身实测值 `{x:0.5, y:0.9479}`（单值修正，见 §7）。
  根因修复（按 spec 尺寸分桶，不跨档刷 pivot）建议**另案**，属 `process.mjs` 逻辑改动，不在本批。

### 4.3 判定 B：`attack-a` —— 比方案 §R10 预警**更隐蔽**：不是"判 FAIL"，是**完全没门禁**

实测 `layout.mjs:4`：

```js
const VARIANT_RE = /-(?:v|skill-a|skill-b|skill-c|entrance|walk-[a-fs]|broken|tombstone)$/;
```

**`attack-a` 不在其中**。于是：

- `familyKey('summon-oathkeeper-attack-a')` → **原样返回 `summon-oathkeeper-attack-a`**（不剥后缀）；
- `applyTemporalGates` 里它独成一族、`base = 它自己`、`members = [它自己]`、`pairs = {}`
  → **一条时间轴比较都不做**，`checks.temporal` 字段**根本不存在**；
- 最终 `✅ PASS` —— 但这是"**没判**"，不是"**判过了**"。

report.json 实证：

```
family: summon-oathkeeper-attack-a | base: summon-oathkeeper-attack-a
  members: ['summon-oathkeeper-attack-a']      ← pairs 为空
summon-oathkeeper-attack-a  PASS  spec=192x192  temporal=ABSENT
```

**若日后把 `attack-a` 补进 `VARIANT_RE`**，按实测指标会是什么结果（已算好，供后续批直接用）：

| 口径 | hypot 门限 | 面积门限 | 实测 hypot **5.85** / 脚底 0 / 面积 **19.4%** | 结果 |
|---|---|---|---|---|
| band128 **idle**（`variantKind` 不识别 `-attack-a` → 落 base/idle 默认） | 4 | 15% | 超 hypot 与面积 | ❌ **FAIL** |
| band128 **walk**（若同时给 `variantKind` 加 `attack` 档，与 walk 同档） | 6 | 25% | 均在线内 | ✅ **PASS** |

> 建议后续批（独立）：`VARIANT_RE` 补 `attack-[ab]`，**同时**在 `variantKind()` 加 `attack` 档
> （推荐与 `walk` 同档 6/0/25%，劈砍是全身动作、姿态变化本就大于呼吸）。
> **只改 `VARIANT_RE` 不改 `variantKind` 会引入一个假 FAIL。**

### 4.4 判定 C：walk-b / walk-d 越界 = **方案 §R10 成真**（记录，不阻断）
