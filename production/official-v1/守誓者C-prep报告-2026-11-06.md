- `:24` —— `COMBAT_128_LOCK_PLAN['hero-cassandra']`

### 1.2 `COMBAT_128_LOCK_PLAN` 追加 + **为何 `-v`/`walk`/`skill` 不进表**

改后（`frame-specs.mjs:17-27`）：

```js
export const COMBAT_128_LOCK_PLAN = {
  'hero-violet': {...128...},
  'hero-violet-fallen': {...128...},
  'hero-galvan': {...128...},
  'hero-cassandra': { w: 128, h: 128, atlas: 'characters', kernel: 'nearest' },   // ← 本批新增
  'summon-oathkeeper': {...192...},
};
```

**先例依据（照 `hero-violet`，不自创）**：

1. `specAfterCombat128Lock()`（`frame-specs.mjs:33-40`）**先 `familyKey(frameName)` 再查表**：
   ```js
   const family = familyKey(frameName);
   const planned = COMBAT_128_LOCK_PLAN[family];
   ```
2. `familyKey()` 的 `VARIANT_RE = /-(?:v|skill-a|skill-b|skill-c|entrance|walk-[a-fs]|broken|tombstone)$/`（`layout.mjs:4`）会把 `-v` / `-skill-a` / `-skill-b` / `-walk-a..f` **全部剥到 `hero-cassandra`** ⇒ 只写族基名，**变体自动继承**。
3. **violet 先例实证**：`COMBAT_128_LOCK_PLAN` 里**从来没有** `hero-violet-v` / `-skill-a` / `-skill-b` / `-walk-*` 这些键，而 `layout.test.mjs:131` 明确断言 `specAfterCombat128Lock('hero-violet-walk-a').w === 128` —— 即「变体不进表、靠 familyKey 继承」本来就是既定约定。
4. 实测复核（本批）：`specAfterCombat128Lock()` 对卡珊德拉 10 帧**全部返回 128 nearest**，`resizeKernel()` 全部 `nearest`。

> 结论：**只需 `'hero-cassandra'` 一行**。给 `-v`/`walk`/`skill` 各写一条属重复且有漂移风险（改档时容易只改一半）。

**⚠ 重要发现（顺带查明，不是本批引入）**：改前那批 hypot 值（11.6 / 15.3 / 21.1 …）是**假的**。`checkExisting()` 用 **spec** 尺寸去量 **PNG 字节**：

```js
// process.mjs:543
const metrics = roundMetrics(silhouetteMetrics(data, spec.w, spec.h));
```

spec 写 64 而 PNG 实为 128 时，等于拿 64 的 stride 去读 128 宽的缓冲 ⇒ 只量到**左上 1/4 窗口**且行错位，度量全歪。spec 改对之后（128 对 128）数值才可信：skill-a 从「11.6」变 **5.82**、skill-b 从「15.3 / 46.2%」变 **5.51 / 24.5%**。

- 这是**契约滞后**的第二个症状（第一个是尺寸 FAIL），且比第一个更危险：它会伪造时间轴 FAIL/SKILL PASS。
- 潜在地雷仍在：只要**任何帧的磁盘尺寸 ≠ spec**，`--check` 的度量就不可信。建议另案把 `checkExisting()` 改为 `silhouetteMetrics(data, info.width, info.height)`（1 行），**本批未动**（边界外）。
- 剩余 3 条 FAIL 是**真**失败且幅度很小（6.5 / 6.7 / 8.3 vs 门限 6px，脚底 ΔY 与面积全在限内），性质与守誓者 `walk-b`(8.3) / `walk-d`(7.8) **完全同类**（重装大步幅剪影横向摆幅大）。不阻断批 C。
