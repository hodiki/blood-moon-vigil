## 2. `resolveFrameSpec` 的匹配机制（以及我照哪个既有模式写）

`tools/asset-pipeline/frame-specs.mjs` 是**三级**匹配，顺序固定：

```
resolveFrameSpec(name)
 ① EXPLICIT[name]            ← 显式表优先（唯一能表达「与族基帧不同尺寸」的地方）
 ② isAnimationVariant(name)  ← layout.mjs 的 VARIANT_RE：
       /-(?:v|skill-a|skill-b|skill-c|entrance|walk-[a-fs]|broken|tombstone)$/
       命中则 familyKey(name) 反查 EXPLICIT[族基帧] → 继承同画布/同图集
 ③ 前缀规则（upg- / wslot- / proj- / relic- …）→ 全不中返 null
```

**决定性事实（本批的技术核心）**：`attack-a` **不在** `VARIANT_RE` 里，`familyKey('summon-oathkeeper-attack-a')` 返回自身，所以 ②**不会回退**到 `summon-oathkeeper` → 批 A 之前它必返 `null` → `pack.mjs:94`（`if (!spec || spec.atlas !== atlasKey) continue;`）静默跳过 ⇒ 劈砍帧永远进不了图集。这就是方案 §1⑥ 说的阻断级缺口。

反向说明：`-walk-a..d` **本来就**能被 ② 兜住（批 A 前实测返 `{w:48,h:48}`，见 §3 附表），但会继承旧 48，且没有任何显式可读的契约行。

**我照哪个既有模式写的**：照文件里**已落地的 128 英雄写法**——`hero-violet-walk-a..f` / `hero-violet-skill-a/b` 是**逐帧显式列出** `{w:128,h:128,atlas:'characters',kernel:'nearest'}`，而不是靠 ② 兜。守誓者 192 是同一族的「更高一档」，照抄该模式：**7 帧逐条显式 + `kernel:'nearest'`**，与 `COMBAT_128_LOCK_PLAN['summon-oathkeeper'] = {w:192,h:192,kernel:'nearest'}`（该表早写 192、从未落地）对齐。

> ⚠ `frame-specs.mjs` 的表只有 `w / h / atlas / kernel` 四个字段，**没有 footY**。所以「脚底 y=191」**写不进规格表**——它是资产属性，靠批 B「直接拷源图、绝不跑 process.mjs」保住。我把这句话写进了代码注释，防止下一个人以为规格能锁脚底。

1. **资产不存在**：192 墓碑图未出，改 192 = 契约与资产永久不一致（`--check` 尺寸项必红）。

> 结论：**墓碑 48 是"有意混档"，不是遗漏**。已在代码注释里写死这句，批 B/C 的人看到不会当 bug。
