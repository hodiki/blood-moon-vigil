## 二、D1 三桶实测值

**测量方式**：以工程实现 `damageBucketEquiv()/survivalBucketEquiv()` 实测（临时测量用例打印后已删除），并经 `talent-tree-b5.test.ts:61-71` 独立真值断言复核。

| 桶 | 口径 α 实测 | 红线 | 判定 | 余量 |
|---|---|---|---|---|
| 伤害（damage） | **6.10%** | ≤ 8% | ✅ | 1.90pp |
| 生存（survival） | **3.41%** | ≤ 6% | ✅ | 2.59pp |
| 合成（d + s） | **9.51%** | ≤ 10% | ✅ | **0.49pp** |

**明细（折算系数 × 可购层数）**：
- 伤害 = `a_attack`(0.4×2) + `a_attack_2`(0.4×1) + `a_damage`(1.2×2) + `a_damage_2`(1.2×1) + `a_attack_speed`(0.5×**1**) + `a_cooldown`(0.4×2) + `br_edmund_2`(0×2) = **6.1**
- 生存 = `a_life`(0.47×2) + `a_life_2`(0.47×1) + `a_move_speed`(0.5×2) + `a_heal_efficiency`(0.5×2) + 6 项 `br_cassandra/violet/galvan`(0×2) = **3.41**

**对照（修复前状态）**：EN-02 修复前 `_2` 子节点因 id 失配被静默漏算 → **假 PASS**；补键后 α 实算曾为 **10.7%（越线）**。EN-12 降档后落 **9.51%**，与 `gdd-talent-tree.md` v1.3 §6.1 目标锚（6.1/3.4/9.5）一致。

**关键机制澄清（防误改）**：A-13 假 PASS 的根因是**查表键失配**（`node.id` 精确匹配不到 `_2` 独立 id，被 `if (per)` 静默跳过），**非遍历遗漏**——遍历本身完整。故 EN-02 只改查表归一化，**未动遍历逻辑**。

#### 5.1 ⚠ `npm run build` 失败 — 预存缺陷（**非 EN-16 引入**）调查报告 【**根因结论已被 §5.2 更正 / 撤回**，原文保留留痕】

- **现象**：`vite build` 在 `index.html` 内联 `<style>` 的 HTML 代理阶段报错 —
  `[vite:html-inline-proxy] Could not load …/index.html?html-proxy&inline-css&index=0.css …: No matching HTML proxy module found`（退出码 1）。
- **独立性证据（三步定位）**：
  1. `git stash push` **仅暂存本人 3 个文件**后重跑 `npm run build` → **同样失败**（退出码 1）；随后已 `git stash pop` 还原。→ **与 EN-16 改动无关**。
  2. **最小复现探针**：在仓库内建独立最小 vite 工程（`index.html` 含内联 `<style>` + `main.js`）`vite build` → **成功**（退出码 0）。→ 非同源内联 CSS 的通用缺陷。
  3. **配置二分定位**：用**等价「纯对象」临时配置**（相同 `base/alias/build`，但**不 import `vite`/`vitest/config`**）跑 `vite build` → **成功**（退出码 0，产出 `dist/index.html` + `dist/assets/index-*.js`，约 3.5 MB）；再加回 `import { defineConfig } from 'vite'`（或 `vitest/config`、甚至仅 `import 'vite'`）→ **必失败**。
- **根因结论**：仓库 `vite.config.ts`（`import { defineConfig } from 'vitest/config'`）在本环境（Windows + Node 22.22.2 + `vite@6.4.3`）触发 **vite 双实例 / HTML 代理缓存键失配**（对应 Vite issue #18228 的 Windows 路径/实例类问题）。`node_modules` 仅一份 `vite@6.4.3`（vitest 3.2.7 peer `^5||^6||^7`）。**纯对象配置下构建成功即证明：代码库（含 EN-16 改动）可正常打包**——失败是**配置/工具链层**问题。
- **未处置原因**：`vite.config.ts` / `package.json` **不在本任务硬约束允许改动范围**（且为共享文件，工程批 C 同期在改）。→ 列为**待主理人裁决项**（见 §6-1）。
- **供裁决的可选处置**（均不在本批授权内，仅登记）：
  - a) 将 `vite.config.ts` 的 `defineConfig` 改为**就地纯对象导出**（去掉 `vite`/`vitest/config` import），或改用 `--configLoader` 兼容写法；
  - b) 升级 `vite`（或对齐 vitest/vite 版本）；
  - c) 规范化构建机路径大小写/壳环境（Git Bash / cmd.exe / PowerShell 三处均复现失败，故此项不适用——**已排除**）。

**流程经验（登记 · 建议纳入门禁 SOP）**：

> **并行写任务的线，不要并行跑全量门禁。** `npm run build` / `vitest run` 会**争用共享缓存**（`node_modules/.vite`）**与输出目录**（`dist/`），产生**间歇性假失败**（false failure）。门禁应**由主理人在收尾后统一跑**，或各线**错开门禁时刻**；遇到门禁失败**先排除并发**，再判定是否真缺陷。
