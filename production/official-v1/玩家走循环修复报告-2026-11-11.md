## 1. 根因（已由主理人定位，本次复核确认）

`src/fx/anim.ts` `playVisual()` 的原守卫：

```js
// 改前（src/fx/anim.ts:202，git rev 0c6bade）
if (scene.anims.exists(start) && (cur === idle || !sprite.anims.isPlaying)) {
  playEntity(sprite, start);
  return;
}
if (cur === start && sprite.anims.isPlaying) return;
playEntity(sprite, move);   // ← 永远执行不到
```

`start`（`${base}-walk-start`）由 `addIdleMovePair()` 建成 **单帧 + `frameRate: 6` + `repeat: 0`**（`anim.ts:129-134`）：

```js
scene.anims.create({ key: startKey, frames: [{ key: 'characters', frame: start }], frameRate: 6, repeat: 0 });
```

⇒ 166.7ms 后动画自然结束，`sprite.anims.isPlaying` 变 `false`，而 **`anims.currentAnim.key` 仍停留在 `start`**（Phaser 不在播完后清 `currentAnim`）。
下一帧守卫第二项 `!sprite.anims.isPlaying` 为真 → **重播 `start`** → 再次 166.7ms 后结束 → **自复燃死循环**，`move` 永远进不去。

命中该缺陷的实体 = 图集里存在 `*-walk-s` 的角色，全库仅 2 个（`ls assets/frames | grep walk-` 实测）：

```
hero-violet-walk-s.png   → 薇奥莱（hero_violet → visualFrame 'hero-violet'）
player-walk-s.png        → 守夜人（hero_edmund → visualFrame 'player'，见 frame-registry.ts:28）
```

**恰好就是玩家可玩的两个角色**，这正是用户「只有薇奥莱出问题」的观感来源。
其余英雄（`hero_cassandra`、`hero_galvan`）帧表无 `-walk-s`，`exists(start)` 为 false，**不受影响**。

## 2. 改前 → 改后

**改后（`src/fx/anim.ts:205-219`，实测行号）：**

```js
if (moving) {
  // start 正在播 → 等它播完（不打断、不重播）
  if (cur === start && sprite.anims.isPlaying) return;          // :209
  // 仅「从 idle 起步」播一次 start；播完后 cur 仍是 start → 不命中此分支，自然落到 move
  if (scene.anims.exists(start) && cur === idle) {              // :211
    playEntity(sprite, start);
    return;
  }
  playEntity(sprite, move);                                     // :215
  return;
}
```

要点：
1. **删除** `!sprite.anims.isPlaying` 这一自杀式条件（它是自复燃的唯一燃料）。
2. 把「start 正在播则早退」提到最前（原在中间，逻辑上等价但对新守卫是必要前置）。
3. `cur === idle` 成为播 `start` 的**唯一**入口 ⇒ start 只可能在「离开 idle 那一刻」播一次。
4. `move` 的 `repeat:-1` 不变，进入后稳定循环。

**导出变更**：`function playVisual` → `export function playVisual`（仅为单测可驱动，按主理人指示**不重构模块**）。
`git diff src/fx/anim.ts` = +13 / −3 行，除上述守卫与导出外**零改动**。

## 5. `start` 时长是否调整 —— **不调整**（保持 `frameRate: 6` = 166.7ms）

主理人要求「实测判断，若要调须给理由」。我的判断是**保持原值**，依据三条实测数据：

**① 166.7ms 恰好等于走循环自身的一帧时长，读作「一个节拍」而非「额外卡顿」。**
6 帧走循环 `walkFrameRate()` = 6.5fps ⇒ 每帧 153.8ms；4 帧为 6fps ⇒ 166.7ms。`start` 在 6fps 下 = 166.7ms，与循环帧时长同量级。即「离站停留」不是插在步态之外的额外停顿，而是被感知为**步态的第 0 帧**。

**② `walk-s` 不是「站立图重复」，是真正的侧身预备姿（用户症状不是它）。**
像素实测（`assets/frames/`，128×128，RGB 均差）：

| 帧对 | 均差(0–255) |
|---|---|
| `hero-violet` vs `hero-violet-v` | **0.00**（idle 变体与基帧完全相同 → idle 实际是静止单帧） |
| `hero-violet-walk-s` vs `hero-violet` | 107.16 |
| `hero-violet-walk-s` vs `hero-violet-walk-a` | 116.64 |
| `hero-violet-walk-a` vs `hero-violet-walk-e` | 63.05 |

即 `walk-s` 与站姿差 107（**远大于**两个相邻走帧之间的 63）——它是一个**独立且明显不同的 Pose**，不是「同一张站立图」（idle 基帧与 `-v` 才是彼此 identical 的那一对）。放大对图（`tmp/nv30-violet-walk-zoom.png`）可见：**idle 是正面朝向、`walk-s`/`walk-a`/`walk-e` 都是侧身**。故 `walk-s` 承担「正面 → 侧身」的转面预备，保留 167ms 让它可读，是**有利**而非卡顿。

**③ 用户症状的成因是「永不进 move」，不是「start 太长」。**
修复前 40 帧采样里 `move` 出现 **0 次**；把 `start` 从 6fps 调到 12fps 只会让「永远同一张图」变成「167ms 后依然同一张图」，**改时长治不了这个 bug**。故本次不混入时序调参（也符合「改动要单独说明、别偷偷混进修复」的要求）。

> **如后续用户仍觉得「起步顿一下」**：唯一旋钮是 `anim.ts:132` 的 `frameRate: 6`。给定 `startMs = 1000 / frameRate`：15fps → 66.7ms（≈4 帧 60fps）、12fps → 83.3ms、10fps → 100ms。我的建议值若真要动是 **12fps（83.3ms）**——约半个走帧节拍，仍保留转面可读性。**本次未改**。

## 9. 未做 / 存疑项（交主理人裁决）

1. **未做视觉终判**：本报告只证明「正确帧在播且帧在变」，**是否「好看」仍须用户在真机/浏览器目视**（我的结论来自 anim/frame 字段 + 像素差，不等于肉眼观感）。建议用户实测：开局按 `d` 走 2 秒，看是否仍有「漂浮」感。
2. **idle 的「变体」实为同一张图**：`hero-violet` 与 `hero-violet-v` 像素均差 **0.00**（`player`/`player-v` 同）。`idleCycleFrames()` 仍建 `[base, base]` 的 1.4fps yoyo → 名义上是 2 帧循环实为静止。**属美术/资源重复，不在本任务边界**（严禁改 assets），仅登记。
3. **正面 idle → 侧身走 的转面跳变**：idle 帧是正面、所有走帧是侧身，起步瞬间必然有一次「正面→侧身」的硬切。`walk-s`（167ms）实质上在承担这个过渡。若用户觉得转面太生硬，正确解法是**补正面→3/4 侧的过渡帧（美术活）**，不是调 `frameRate`。建议进 `m4-backlog`。
4. **`start` 时长保留 6fps 是我的判断，非用户实测结论**：若用户复测后仍报「起步顿一下」，按 §5 尾注改 12fps（83.3ms）即可，一行改动 + 需重跑本套单测的时长锚点断言（断言区间 [160,200) 需同步为 [80,100)）。
5. **探针脚本 `tmp/nv30-walk-probe.mjs` 未入库**（沿用批 E/F 惯例，临时 QA 工具留在 `tmp/`）。若希望长期留作走帧回归探针，可移到 `tests/smoke/` 并登记进 test-framework。
