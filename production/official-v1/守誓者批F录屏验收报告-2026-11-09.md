## 2. ⭐ 滑步量化判定（本批核心增量）

### 2.1 理论所需步幅（口径重述，与任务书一致）

```
FOLLOW_SPEED = 120 px/s            （oathkeeper-runtime.ts:48）
WALK_FRAME_MS = 330                （oathkeeper-view-sprite.ts:WALK_FRAME_MS）
⇒ 每帧位移 = 120 × 0.330 = 39.6 px
⇒ 整圈 4 帧 × 330ms = 1320ms → 一圈位移 = 120 × 1.32 = 158.4 px
```

### 2.2 美术实际步幅（逐帧像素实测）

**方法**：走帧是 in-place 循环，脚相对画布向后滑 → **帧内「着地脚」的相对水平位移就是美术画的位移**。
用三种独立口径互相校验：

| 口径 | 做法 | 结果 |
|---|---|---|
| ① 鞋底重心 | 取最低 5 行（`y∈[187,191]`）不透明像素，按列聚合后在**最大间断处**切成左右两块，各求 x 重心 | 见下表 |
| ② 底部带 NCC | `y∈[150,191]` 的 alpha 场做归一化互相关，搜最优水平平移 | `a→b=−10, b→c=−2, c→d=0, d→a=+10`（闭环和 = −2 ≈ 0，**方法自洽**，且与 ① 同量级） |
| ③ 逐列最低行 | 每列取最低不透明行，看"脚底轮廓线" | 与 ① 一致（`a/c` 单簇、`b/d` 双簇） |

**实测（①②③ 收敛后的表）**：

| 帧 | 着地带分块 | 着地间距 |
|---|---|---|
| `walk-a` | 单块 `x=99..119`（块内最大间隙 1px）| **8.80 px** → 只有**一只脚**着地（passing）|
| `walk-b` | 左 `84..106` cx=96.45 / 右 `115..135` cx=122.04 | **25.59 px** → 双脚分开（contact）|
| `walk-c` | 单块 `x=99..119` | **9.81 px** → 一只脚着地（passing）|
| `walk-d` | 左 `84..106` cx=96.93 / 右 `112..137` cx=121.08 | **24.15 px** → 双脚分开（contact）|

**⇒ 美术「半步（一个 step）」= 接地帧的双足间距 = (25.59 + 24.15) / 2 = 24.87 px**
**⇒ 整步（一个 stride，4 帧）= 2 × 24.87 = 49.74 px**
**⇒ 美术每帧位移 = 49.74 / 4 = 12.44 px**

> **核实交付单的「半步 ≈ 32px」→ 不成立。**
> 32px 的来历是 `方案 §4-R6` 的"走帧内容宽 74~84、肩宽约 64 → 半步约 32px"，即**拿剪影宽度的一半当步幅**。剪影宽度包含斗篷/剑/斜置的躯干，与"双脚落地间距"是两个量。实测差 **29%**，导致批 E 的 2.5× 估计偏乐观。

### 2.3 滑步比

```
滑步比 = 每帧位移(理论) / 美术每帧位移(实测)
       = 39.6 / 12.44
       = 3.18
```

**判定：FAIL**（阈值 `> 1.8`）

### 2.4 阈值确认（任务书要我确认或修正）

**我确认 `≤1.2 / 1.2~1.8 / >1.8` 这组阈值可用**，理由：

1. **1.2 以内**：脚相对地面每换一个姿势最多多走 20%，在 330ms 的姿势停留内眼睛抓不到 —— 这是 2D 动作游戏的通行舒适区。
2. **>1.8**：每换一次姿势，**地面相对脚走过的距离已经是美术步幅的 1.8 倍以上**，也就是"地面走得比脚还多"，大脑改判为"滑行"。1.8~2.0 是行业里常见的"能看出但能接受"的上沿。
3. **我再加一条绝对量交叉判据（建议并入阈值表）**：
   ```
   每姿势位移 / 角色内容宽 = 39.6 / 78 = 0.51
   ```
   即"每换一个姿势，人往前挪了**半个身宽**"。这个绝对量本身就已经很刺眼，而且它**不依赖帧时长**——所以当两个口径（比值 + 绝对量）都报警时，不必纠结阈值取 1.8 还是 2.0，结论都是"看得出来"。

### 2.5 ⚠ 比滑步比更早暴露的问题：这 4 帧不是交替步

把接地帧的左右脚重心摆在一起：

| | 左足重心 | 右足重心 | 间距 |
|---|---|---|---|
| `walk-b`（contact）| 96.45 | 122.04 | 25.59 |
| `walk-d`（contact）| 96.93 | 121.08 | 24.15 |
| `walk-a`（passing）| — 单簇 cx≈107.8 | | 8.80 |
| `walk-c`（passing）| — 单簇 cx≈107.8 | | 9.81 |

**`b ≈ d`、`a ≈ c`** —— 两次接地**都是同一只脚在前**，不是"左脚前 → 右脚前"的交替。
也就是说：这组图是 **「原地跺步（2 个姿势 + 变体）」**，不是真正的行走循环。
后果：**即便把滑步比调到 1.0（完全不打滑），看久了也会读成"同一只脚反复迈"**。
这条不在本批修复范围内（要美术补帧），**登记为需修项 M-2**。

### 2.6 三个方案的成本对比（含我另算的 2 个）

| 方案 | 滑步比 | 持续跑动多久失去 150px 替身圈* | 改动 | 人日 | 判定 |
|---|---|---|---|---|---|
| **现状**（120 / 330ms）| **3.18** | **0.78 s** | — | — | FAIL |
| (a) `FOLLOW_SPEED` 降到 90 | 2.40 | **0.62 s（更差）** | 1 常量 | 0.02 | 仍 FAIL，且恶化掉队 |
| (b) 常态 90 + `dist>阈值` 提速 180 | 常态 **2.40** / 追赶 **4.79** | 不掉队 | ~4 行 + 2 常量 + 2 单测 | 0.10 | 常态仍 FAIL；且"追"会是常态（见注） |
| (c) 美术加大步幅到 ≤1.2 | 需半步 **66px**（现 24.9，**×2.65**）| — | 重画 walk ×4 | 1~2 | **解剖不可行**：脚要张到 66px，而他内容宽只有 74~84px |
| **(d) 只改帧时长 330 → 180ms**（我新增）| **1.74**（CONCERNS 上界内）| 0.78 s（不变）| **1 常量 + 注释** | **0.02** | **建议先试这个** |
| **(e) 位移驱动步进**（我新增）| **1.00（构造性零滑步）** | 0.78 s（不变）| 壳内 ~6 行 + 1 常量 + 单测 | 0.15 | 最彻底，但步频 9.7fps |
| (f) 接受现状 | 3.18 | — | 0 | 0 | FAIL 记录在案 |

\* 掉队算式：`(150 − 60) / (235 − v)`；玩家 `MOVE_SPEED=235`（`config/balance/player.ts:12`）、锚距 60、替身圈 150（`OATHKEEPER_LEASH`）。跟随逻辑是"追到 60px 以内"的**无提速直线逼近**（`oathkeeper-runtime.ts:163-171`），**没有追赶提速**。

**逐条说明**

- **(a) 降到 90 不成立**：滑步比只从 3.18 降到 2.40（仍 FAIL），同时把"失去替身圈"的时间从 0.78s 缩到 0.62s。**两个方向同时变差**，不要选。
- **(b) 追赶提速**：能给玩法兜底（掉队不再无界），但**不能改善观感**——因为玩家常态在跑，`dist>120` 几乎恒成立，他会一直挂在 180 的追赶档（滑步比 4.79，比现状更差）。建议把它当**独立的玩法 ticket**（解决掉队），不要指望它解决滑步。
- **(c) 不可行**，已量化：半步要从 24.9 涨到 66（1.2 阈值）或 44（1.8 阈值），腿长（腰→脚 ≈ 90px）摆不出来。
- **(d) 我建议先试 180ms/帧**：
  - 每帧位移降到 `120 × 0.180 = 21.6px`，滑步比 **1.74**；
  - 步频 = 1/0.18 = **5.56 姿势/秒**，比交付单当年否掉的 155ms/帧（6.45 姿势/秒）**还慢**——所以"像抽搐"这个顾虑在该区间**不成立**（当年是凭想象判断的，本批给了区间）；
  - 一圈 720ms ≈ **2.78 步/秒**，落在正常成人步频（1.8~2）与快走（2.8~3）之间，对板甲重甲偏快但可读；
  - 代价：姿势停留从 330ms 缩到 180ms，看得到"接地/经过"的交替（反而**比现在更容易数出 a→b→c→d**）。
- **(e) 位移驱动步进**：把 `walkElapsedMs += dt*1000` 换成"每累积 `12.44px` 位移进一帧"，**滑步比结构性等于 1.00**，任何速度都不打滑；代价是速度越高步频越快（120px/s → 9.68 帧/秒）。若日后 `FOLLOW_SPEED` 要上调，这是**唯一不冲突的解法**。

> **我的建议**：主理人若接受"动一个常量"，先上 (d) 再录一次 30 秒复核；若 (d) 的 180ms 观感仍觉得碎，改上 (e)（0.15 人日，且不再受速度变化影响）。

| vf=500 | 20.00s | `summon-oathkeeper` | idle |
| vf=508 | 20.32s | `-walk-a` | move |
| vf=524 | 20.96s | `-walk-b` | move |
| vf=537 | 21.48s | `-walk-c` | move |
| vf=555 | 22.20s | `-walk-d` | move |
| vf=568 | 22.72s | `-walk-a` | move |

| vf=592 | 23.68s | `-walk-c` | move |
| vf=596 | 23.84s | `-attack-b` | attack（刷敌后的撕咬，见 §3.2）|

⇒ **a→b→c→d→a→b→c**，顺序正确、无乱序、无跳帧；`d→a` 正确闭合。同一张图见 `守誓者批F-2walk-2026-11-09.png`（每格带帧号/时刻/帧名）。

**证据 B（运行时全量记录）**：一次会话 734 个 rAF 采样，共 **35 个 walk 帧段**，帧序统计：

| 帧 | 出现次数 | 平均停留（墙钟）|
|---|---|---|
| `walk-a` | 18 | 290ms |
| `walk-b` | 9 | 359ms |
| `walk-c` | 5 | 330ms |
| `walk-d` | 3 | 526ms |

> **停留时长不可直接当 330ms 的验证**（诚实标注）：headless 下 rAF 间隔中位 **98ms（≈10fps）**，且 `clampDelta` 会钳制 delta → 游戏内时钟约为墙钟的 0.5~0.6×，所以墙钟停留约 500ms 而游戏内名义 330ms。**帧序判据不受影响**（帧序是"名次顺序"，与速率为无关量）。`walk-a` 偏多是因为**每 1s 一次的撕咬会把 walk 累加器归零**（`frameFor` 里"离开 move 一律归零"），所以每次都从 a 重新起步——这是**设计意图**，不是丢帧。

**⚠ CONCERN（本批新发现）**：`a≈c`、`b≈d`，两次接地同一只脚在前 → 是"原地跺步"而非交替步（见 §2.5）。**帧序合格，步态本身不合格**，登记 M-2。

### 3.2 判据 2 · 撕咬帧出现 —— **PASS**

- **两张帧都已取到真值**（不是伪造 `sinceBiteMs`）：
  - `守誓者批F-3attack-2026-11-09.png` → `frame=summon-oathkeeper-attack-a`, `viewState=attack`
  - `守誓者批F-3attack-b-2026-11-09.png` → `frame=summon-oathkeeper-attack-b`, `viewState=attack`
- **信号链是真接通**：本批**没有碰 `sinceBiteMs`**，而是用 `spawner.spawnOneById('enemy_g1_1', …)` 在守誓者脚下刷了 **3 只真敌人**，让 `tickBite()` 真的返回 `dealt > 0` → `PlayScene` 接住 → `notifyBite()`。能拍到 attack 帧本身就是这条链通的证据。
- **「~150ms 后回落」的证据口径**（诚实标注）：运行时记录到 **24 个完整 attack 窗口**，**每一个**都以 `attack-a → attack-b → 回 idle/walk` 收尾；窗口墙钟时长 78~112ms。**但 150ms 这个数不能靠录屏证**——25fps 视频 / 10fps headless rAF 都分辨不了 150ms 级窗口（采样间隔就有 98ms）。150ms 的准确性由**壳单测**（36 例，`ATTACK_HOLD_MS=150` 与 `ATTACK_FRAME_A_MS=75` 均为双向边界断言）保证，录屏只证"两帧都真的出画了、且会回落"。

### 3.3 判据 3 · 墓碑出现 + yOffset 生效 —— **PASS（附一条观察）**

## 8. 未验证 / 存疑（如实列）

1. **`reviveProgress` 进度环**：方案 §3.5 建议的"墓碑复活进度环"**仍然没有**——复活过程在局内**零可见反馈**（本批只验证了"碑出现→碑消失→人回来"，玩家不知道自己快把他救活了）。属既有缺口，登记在案。
2. **真实 60fps 下的观感**：本批所有录屏是 headless（10fps，`clampDelta` 钳制 delta）。**帧序、帧名、坐标、滑步比都与帧率无关**（滑步比用的是 `FOLLOW_SPEED × 330ms` 与像素实测），但"看起来顺不顺"仍需真机 60fps 一次确认。
3. **150ms 撕咬窗口的时长精度**：录屏/采样都分辨不了（见 §3.2），只能靠单测保证。
4. **`hasTombstoneFrame192 = false` 分支**：192 墓碑图仍未产出，`Y_OFFSET_TOMBSTONE_192` 从未被真实走到（只在单测里）。
5. **升级卡期间的观感**：M-5 只说"采样会失真"，未评估"升级卡期间守誓者在画面上停住"是否会被玩家读成卡顿（因为它本来也在动）。
