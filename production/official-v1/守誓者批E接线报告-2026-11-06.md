## 2. 壳的接口与「决策器 ↔ 壳」数据流

```ts
// src/weapons/companion/oathkeeper-view-sprite.ts
export class OathkeeperViewSprite {
  readonly sprite: Phaser.GameObjects.Sprite | null;   // 缺纹理/缺帧 → null（静默降级，不崩）
  constructor(
    scene: OathkeeperViewSpriteScene,   // 只依赖 add / textures（Pick<Phaser.Scene,…>）
    runtime: OathkeeperRuntime,
    player: { x: number; y: number },
    textureKey?: string,                // 默认 'characters'
  );
  update(dtSeconds: number): void;       // 每帧：算 speed → 决策 → 应用
  notifyBite(): void;                    // 唯一事件性输入（dealt > 0 时调用）
  get viewState(): OathkeeperViewState;  // 调试/自证用
  destroy(): void;                       // 幂等
}
```

**为什么壳能单测**：`import type Phaser from 'phaser'`（**type-only，编译期擦除**）+ 精灵只走 8 个方法
（`setVisible/setTexture/setFlipX/setPosition/setDepth/setScale/setRotation/destroy`）
+ `frameFor`/`measureSpeed` 全在类内 → vitest `environment: 'node'` 用 FakeSprite 全量驱动，
**不需要 jsdom/canvas**。这也是批 D 留下的「Phaser 壳无法单测」缺口的一种解法（依赖面收窄到可枚举）。

数据流（每帧一次，**纯轮询 + 一个 bite 信号，无事件总线**）：

```
rt.state.phase / x / y ──┐
player.x ────────────────┤ (prevX,prevY) 差分 + 瞬移护栏 → speed
sinceBiteMs（notifyBite）─┴→ resolveOathkeeperView(…) → out{state, visible, flipX, yOffset, depth}
                                                          │
                                     frameFor(out.state) ─┴→ 帧名（walk 累加器 / attack 相位）
                                                          ↓
              setVisible · setTexture(换帧时) · applyCombatDisplayScale(换帧时)
              · setFlipX · setPosition(st.x, st.y + yOffset) · setDepth(30)
```

**职责边界（不让壳重新判定任何态）**：`tombstone` 压过 `attack`、`attack` 压过 `move` 的优先级、
yOffset 的 −32 / +37÷6、depth、flipX 死区 —— **全部由决策器算**；壳只做「按 state 选帧名 + 落地」。
壳自己只持有 4 个东西：`prevX/prevY`、`walkElapsedMs`、`sinceBiteMs`、`lastFrame/lastState`。

## 3. 三态换帧表（含 attack a→b 时序）

| `state` | 帧 | 时长 | 备注 |
|---|---|---|---|
| `idle` | `summon-oathkeeper` | — | **不切 `-v`**（裁决①） |
| `move` | `-walk-a → -walk-b → -walk-c → -walk-d`（循环回 a） | **330ms/帧**（一圈 1320ms） | 起步必从 a 帧起 |
| `attack` | `-attack-a`（起手）→ `-attack-b`（收势） | **75ms + 75ms = 150ms** | 与 `ATTACK_HOLD_MS` 严丝合缝 |
| `tombstone` | `-tombstone`（旧 48 图） | — | `applyCombatDisplayScale` → 2.667；`yOffset = +37/6` |
| `hidden` | 不渲染 | — | `visible=false`（`gone` / 未启用） |

### attack 时序（实测）

| 距撕咬 | 0–74ms | 75–149ms | ≥150ms |
|---|---|---|---|
| 帧 | `-attack-a` | `-attack-b` | 回 `idle` / `move` |

**为什么两帧各 75ms（而不是方案 §3.2 建议的 100+100）**：决策器的 `ATTACK_HOLD_MS = 150` 是**批 D 已定稿**的
窗口（64 用例覆盖，本批不得改）。方案建议的 100+100=200ms 会**超出窗口 33%** →
后 50ms 决策器已返回 `idle`/`move`，出现「砍到一半突然站直」的截断；
60fps 下 75ms ≈ 4.5 帧，起手与收势**都看得见**，且**不需要任何美术产出**。
故取 `ATTACK_FRAME_A_MS = ATTACK_HOLD_MS / 2`（**写除法不写字面量**：窗口若调整，两帧自动跟随，永不越界）。

**为什么用单帧不行**：150ms 单帧在 1.0s 的撕咬间隔里只「闪一下」，读不出「抬手→落下」；
双帧是同一动作的起手/收势，是最短的「可读挥砍」配置。

### 330ms 依据（交付单 §3.3 硬性值，非调参项）

4 帧只覆盖**两个半步**；按角色动画的 ~155ms/帧 播，在 192 画布上会像抽搐（交付单实测结论）。
330ms × 4 = 1.32s/圈 ≈ 1.5 步/秒，与板甲重甲缓慢踏步的观感一致。

**walk 累加器的边沿语义**：只在**连续 move 帧**累加；离开 move（idle / attack / tombstone / 瞬移 /
未启用）一律归零 → 下次起步必从 `-walk-a` 起（否则从 c 帧起步像崴脚，方案 §3.2）。

## 4. 瞬移护栏：判定式与阈值

**位置纪律**：必须在「算 speed」处（`measureSpeed`，壳内 `:255`，调用点 `:217`），**不在**决策器里
（决策器只做 `speed > 5` 分档，批 D 契约有意如此）。

```
dist = hypot(state.x − prevX, state.y − prevY)
if (!isFinite(dist))        speed = 0        // NaN/Inf 防御
if (dist > 400)             speed = 0        // ← 瞬移护栏（本帧不作 move 判定）
if (dt <= 0)                speed = 0        // 防除零 → Infinity
否则                         speed = dist / dt
```

`TELEPORT_GUARD_PX = 400`（方案 §3.2 原值）的**量化理由**：

- 常规帧：`clampDelta` 上限 **50ms**（`core/time.ts`）× `FOLLOW_SPEED` **120px/s** → 合法单帧位移 **≤ 6px**；
- 极端掉帧：`clampDelta` 硬上限 **250ms** → 合法单帧位移 **≤ 30px**；
- 400px = 常规上限的 **66 倍** / 极端上限的 **13 倍** → **正常跟随永不误判**，真瞬移（复活/重召唤/首帧错位）必被抓到。

**误判后果不对称**（这是敢取"大阈值"的原因）：误判为瞬移只会丢 **1 帧** move（退化为 idle，肉眼不可见）；
漏判的代价也不是 speed 数值本身（决策器只比 5px/s），而是**walk 累加器从 c 帧起跳**。
所以护栏除了把 speed 归零，**顺带把 `walkElapsedMs` 归零**（因为非 move 分支一律归零），一箭双雕。

测试：`瞬移 500px → idle`、`400 边界双向（400 → move / 400.5 → idle）`、`瞬移后复位从 a 帧起`（3 例）。

## 5. `applyCombatDisplayScale` 的调用点（实测行号）

| 行号 | 场景 | 说明 |
|---|---|---|
| `oathkeeper-view-sprite.ts:182` | **构造**（精灵刚建好） | 192 躯干 → `scale 1`；此后到首帧 update 期间不会以错误缩放闪一帧 |
| `oathkeeper-view-sprite.ts:291` | **每次换帧后**（`apply` 内 `lastFrame !== frame` 分支） | 纪律②：48 墓碑 → `128/48 = 2.6667`；回躯干 → 1 |

**为什么只在「换帧时」调**：`setScale` 每帧调用是纯浪费（192 帧下恒为 1）。
`lastFrame` 记录已落地帧名 → 同帧重复不再 `setTexture`+`setScale`（单测已钉死：3 帧不变只 1 次 `setTexture`）。
**不自己写 `setScale(1)`**（方案 §3.4 明确禁止）——否则切墓碑时会忘了改回来。

运行时实测对照：躯干 `scale 1 / displayHeight 192`；墓碑 `scale 2.6667 / displayHeight 128`
（与玩家 128 世界边同口径，正是"48 图放大到 128 世界 px"的预期）。

## 7. `FOLLOW_SPEED`：180 → **120**

依据（R6 滑步）：walk 循环 4×330ms = **1.32s/圈**覆盖 2 个半步，美术踏步 ≈ **32px/步**。
180px/s × 1.32s = 每步 **119px ≈ 3.7×** 美术步幅 → 肉眼"脚不动却在地上滑"。

| 取值 | 每步位移 | 滑步倍数 | 玩家持续跑动时的差速（玩家 235px/s） |
|---|---|---|---|
| 180（旧） | 119px | 3.7× | 55px/s |
| **120（本批）** | **79px** | **2.5×（−33%）** | **115px/s** |
| 90（区间下界） | 59px | 1.9× | 145px/s |

**取区间上界 120 的理由**：跟随是「追到 60px 以内」的**无提速直线逼近**（`runtime.update` 里
`step = min(dist − 60, v·dt)`），跟随速度越低 → 玩家持续跑动时**稳态掉队越远**；
而 **150px 替身圈**（承伤转移 + 强制索敌，`OATHKEEPER_LEASH`）要求他别掉太远。
即在「美术滑步」与「玩法掉队」之间取 120。注释已写进 `oathkeeper-runtime.ts:34-48`（标注 R6 滑步修正）。

**⚠ 未解项（需批 F 拍板，见 §11-B）**：120 与 90 都低于玩家 235，长时间直线冲刺仍会掉队；
滑步也只减了 33%。两者都需要**批 F 录屏**才能定值。
