## 2. 接口最终签名（与方案 §3 的对应）

```ts
export type OathkeeperViewState = 'idle' | 'move' | 'attack' | 'tombstone' | 'hidden';

export interface OathkeeperViewInput {
  phase: OathkeeperPhase;              // 'companion' | 'tombstone' | 'gone'（复用 oathkeeper.ts 的正典类型，type-only import）
  speed: number;                       // px/s，来自 state 位移差
  sinceBiteMs: number;                 // 距上次撕咬毫秒数；Infinity = 从未撕咬
  playerX: number;
  selfX: number;
  hasTombstoneFrame192?: boolean;      // 本批 false → 走旧 48 分支的 yOffset
  prevFlipX?: boolean;                 // 【新增可选】提供时启用 8px 朝向死区（方案 §3.2）
  tombstonePolicy?: 'legacy48' | 'hidden';  // 【新增可选】墓碑精灵策略，默认 'legacy48'
}

export interface OathkeeperViewOutput {
  state: OathkeeperViewState;
  visible: boolean;
  flipX: boolean;
  yOffset: number;                     // 相对 state.y 的脚底线补偿
  depth: number;
}

export function createOathkeeperViewOutput(): OathkeeperViewOutput;
export function resolveOathkeeperView(
  input: OathkeeperViewInput,
  out: OathkeeperViewOutput = createOathkeeperViewOutput(),   // 热路径传 out → 零分配
): OathkeeperViewOutput;
```

## 3. 脚底线 yOffset 完整推导（本批核心计算）

### 3.1 口径三要素

1. **地面线** = 最低不透明像素行的**中心** = `footY + 0.5`（与方案 §3.4 的 `127.5` 同口径）。
2. **锚点** = 默认 `origin (0.5, 0.5)` → 锚点 y = `canvasH / 2`（全仓角色/敌人一致，`player.ts` 也是。
   故**不**用 `setOrigin(0.5, 0.9974)`——集中一处常量偏移，不易被后人误读成特例）。
3. **显示缩放** = `combatDisplayScale(frameW)`（`src/fx/combat-display-scale.ts:8`）：`frameW >= 128 → 1`，否则 `128 / frameW`。

于是「脚在锚点下方的世界 px」`= (footY + 0.5 − canvasH/2) × scale`。

### 3.2 实测数据（2026-11-06 用仓内 `tools/scheme-c/read-png.mjs` 解码取 alpha>0 的最低行）

| 帧 | 画布 | 内容 top | **最低不透明行** | anchor | scale | 脚在锚点下 |
|---|---|---|---|---|---|---|
| `assets/frames/hero-violet.png`（玩家） | 128×128 | 16 | **127** | 64 | 1 | **63.5** |
| `…/review/20261104-oath/sets/summon-oathkeeper-idle.png`（新 192 躯干） | 192×192 | 25 | **191** | 96 | 1 | **95.5** |
| `assets/frames/summon-oathkeeper-tombstone.png`（旧 48 墓碑） | 48×48 | 10 | **45** | 24 | 128/48 = 8/3 | **57.3333** |

> 交叉校验：`sets/attack-a` 最低行同样 **191**、`x192v2/attack-b` 亦 191 → 192 交付集同基准入盒，
> 与方案 §1「额外机会」的结论一致（所以 `Y_OFFSET_BODY_192` 对 idle/move/attack **三态通用**，无需分态）。

### 3.3 常量

```ts
PLAYER_FOOT_OFFSET        = 63.5            // 玩家 128 画布英雄
BODY_192_FOOT_OFFSET      = 95.5            // 守誓者 192 躯干
TOMBSTONE_48_FOOT_OFFSET  = 57 + 1/3        // 旧 48 墓碑 × 8/3

Y_OFFSET_BODY_192      = 63.5 − 95.5      = −32          // 精确整数
Y_OFFSET_TOMBSTONE_48  = 63.5 − 57.3333   = 37/6 ≈ +6.1667
Y_OFFSET_TOMBSTONE_192 = 63.5 − 95.5      = −32          // 未来 192 墓碑（脚底同 191）
```

### 3.4 三条结论

1. **躯干 `-32`**：与方案 §3.4 独立吻合（`96 − 191.5 + 127.5 = 32`，整数 32，非近似）。照字面写 `sprite.y = state.y` → 脚**沉到地面下 32px** = 他体高 167 的 **19%**，肉眼立刻看出"站在坑里"。
2. **旧 48 墓碑 `+37/6`（方案未写）**：48 图放大 2.667× 后脚只落在锚点下 57.33px，比地面线**浅 6.17px** → 必须**下移**补偿。若墓碑沿用 `-32`，他会**浮起 6.17px**（比沉 32px 轻微，但"挡伤害的东西飘在半空"同样穿帮）。
3. **未来 192 墓碑 `-32`**：一旦 192 墓碑帧落盘且同基准入盒（脚底 191），把 `hasTombstoneFrame192` 置 `true` 即自动回到 `-32`，**无需改代码**。

1. **墓碑策略默认值 = `legacy48`（方案 §3.5 A 案）还是 `hidden`（任务书 ② 的建议）？**

   **建议 E 批实机目视"脚是否与玩家同一条线"作为最终判据**（方案 §2 批次 E 验收 6）。
3. **文件命名冲突（方案 §2/§3.1 vs 任务书）**：方案批次 D 叫 `oathkeeper-view-state.ts`、

5. **R6（`FOLLOW_SPEED` 180 → 90~120）**：只影响 E 批 walk 帧时与步幅的匹配，**与决策器数值无关**
