# ADR-002：输入抽象——统一移动向量接口，双端输入适配器模式

> 状态：**已接受** · 日期：Phase 3 · 作者：程基岩（工程主程）
> 关联：`architecture.md` §4.1 · 上游：`concepts/concept.md` §8（统一方案：差异只在输入层与渲染层）

## 背景

支柱 1 明确"**走位是唯一操作**"：游戏的全部主动输入只有移动。而双端输入方式完全不同：
- 桌面：WASD + 方向键（离散按键，斜向需归一化）；
- 移动：左半屏虚拟摇杆（连续向量，幅度即速度百分比）。

若把键盘扫描逻辑直接写进玩家移动代码，则玩家模块被迫感知设备、两套分支散落各处，违反 concept §8"战斗/生成/升级逻辑完全共用，差异只在输入层"。同时输入是后续可访问性（重映射键位）与测试（注入模拟输入）的天然切入点。

## 决策

**采用适配器模式，定义统一移动向量接口 `InputSource`，双端各实现一个适配器：**

```ts
// input/input-source.ts（接口签名，详见 architecture.md §4.1）
export interface InputSource {
  getMove(): { x: number; y: number };   // 归一化向量，长度 ≤1（摇杆幅度 = 速度百分比）
  onPauseToggle(cb: () => void): void;
  onTap(cb: (x: number, y: number) => void): void;
  destroy(): void;
}
```

1. **`KeyboardInput`（桌面）**：监听 WASD + 方向键，8 向合并后归一化；`JustDown` 触发暂停。
2. **`TouchInput`（移动）**：左半屏浮动摇杆（`pointerdown` 建底座、拖动算向量、`pointerup` 归零隐藏）；摇杆贴图在 Phaser 内（effects 图集）以保证坐标系一致。
3. **工厂/装配**：`PlayScene.create` 依据 `RuntimeConfig.isMobile` 选择一个适配器注入，**玩家模块只依赖 `InputSource` 接口，完全不感知设备**。
4. **升级选卡/结算的点击由 DOM 覆盖层直接处理**（ADR-004），不进入 `InputSource`；`onTap` 仅保留给未来可能的战斗内点按需求。

## 后果

**正面**：
- 玩家/武器/生成器等战斗代码**零双端分支**——设备差异被完全隔离在 `input/` 目录。
- 可测试性：单测可注入 mock `InputSource`（固定向量）验证移动逻辑，无需真实键盘。
- 可扩展性：未来支持手柄/自定义键位，只需新增适配器，不改业务代码。
- 对齐 art-bible §9 可访问性：重映射/高对比不影响输入层接口。

**负面**：
- 引入一层接口间接（对 Demo 规模略"重"）。
- 虚拟摇杆需自研（Phaser 无内置），触控数学（clamp、死区）要自己写。

**缓解**：
- 接口只有 4 个方法，间接成本可忽略；摇杆数学约 40 行，且放入 `utils/math.ts` 可单测。
- 摇杆**死区**（中心 10% 不响应）与**热区 ≥44px**（art-bible §6）在 `TouchInput` 内统一实现，避免移动端误触。

## 备选方案

| 方案 | 评价 |
|---|---|
| **玩家模块直接读键盘/触控** | 最少代码，但双端分支渗入业务层，违反 concept §8 统一方案；测试困难。**否决** |
| **仅用摇杆、桌面也模拟摇杆** | 桌面键鼠体验差（按键不是连续向量），且斜向归一化仍需处理。**否决** |
| **第三方输入库**（如 `phaser3-rex-plugins` 虚拟摇杆） | 功能全但引入依赖、学习成本与版本风险；自研 40 行足够。**现阶段否决**（可后评估） |

## 验收核对

- concept §8"双端输入统一映射为移动向量" ✔；支柱 1"无手动瞄准/攻击"——`InputSource` 无攻击接口 ✔。
- art-bible §6 触控热区 ≥44×44、桌面 ≥32×32 由适配器与 DOM 层落实（见 control-manifest.md）。
- upgrade-pool §7"移动端摇杆在选卡暂停期隐藏"由 `TouchInput` 在 `GameState` 切 LEVEL_UP 时隐藏实现。
