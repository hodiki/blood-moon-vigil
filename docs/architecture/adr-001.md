# ADR-001：实体管理——对象池 + 组件式数据结构（而非重 ECS）

> 状态：**已接受** · 日期：Phase 3 · 作者：程基岩（工程主程）
> 关联：`architecture.md` §3.2/§3.3 · 上游：`concepts/concept.md` §8（对象池）、`enemies.md` §6、`weapons.md` §6

## 背景

《血月守夜》是幸存者 like：核心压力来自**同屏大量实体**（桌面 400 敌人 + 8 子弹 + 300 宝石 + 200 粒子；移动端同屏 250）。Web 平台最致命的卡顿源是 **GC 停顿**——频繁 `new`/`destroy` 造成的内存抖动与销毁开销。同时系统地图（system-map.md）给出 10 个子系统，玩法实体有明确分层（敌人 4 类面板 + 武器 3 种 + 玩家 + 拾取物），但**实体类型总量很小**。

技术选型摆在面前：是否引入完整 ECS（Entity-Component-System）架构？

## 决策

**采用「对象池 + 组件式数据结构」：**
1. **所有可池化实体**（敌人/子弹/宝石/特效）继承 `Phaser.Physics.Arcade.Sprite`（或 `GameObjects.Sprite`），以 `Phaser.Physics.Arcade.Group` 承载，`maxSize` 设双端上限，`get()`/`killAndHide()` 复用实例，**零频繁 new/destroy**（`architecture.md` §3.2/§3.3）。
2. **实体内部用组件式数据字段**（面板值、状态位、冷却计时器等直接写在实体类上），不引入 ECS 的"实体 ID + 组件注册表 + 系统遍历"三层间接。
3. 跨实体能力（移动/碰撞/伤害）以**服务模块**（`combat/damage.ts`、`spawner/spawner.ts`）统一处理，实体自身只持有数据与"被打"的响应方法，不各自实现伤害逻辑（避免重复实现，对齐控制清单"禁止散落业务逻辑"）。

## 后果

**正面**：
- 复杂度与实体类型规模匹配（4 敌 3 武 1 玩家 1 Boss），开发者（前端出身）心智负担低，无需学习 ECS 概念。
- `Arcade.Group` 自带 `get`/`killAndHide` 生命周期与物理 body 管理，代码量远小于自建 ECS。
- 池上限天然等于性能预算上限（400/250），生成器可精确感知"还能不能生"。

**负面**：
- 组件式继承对"未来状态组合爆炸"（超武合成、异常状态叠加、多角色差异化）扩展性不如 ECS——实体类可能随功能膨胀。
- `Arcade.Sprite` 继承层级固定，若日后需要"非渲染实体"（纯逻辑节点）需另做轻量对象池。

**缓解**：
- 以接口（`Poolable`）约束生命周期，池逻辑与实体实现解耦，未来迁移 ECS 时池可保留。
- 单类实体职责单一（`enemy.ts` 只做移动/受击响应，面板数据放 `enemy-types.ts`），膨胀有上限。

## 备选方案

| 方案 | 评价 |
|---|---|
| **完整 ECS**（如 `perform-ecs`/自研） | 可扩展性最好，但 Demo 规模下基建成本（注册表/系统调度/组件内存布局）远超收益；Web 上还需额外引依赖，违背 Lean 评审"轻量"。**否决** |
| **每帧 new/destroy 实体** | 实现最简单，但 400 实体高频销毁在移动端必然 GC 停顿，无法满足 30fps+ 预算。**否决** |
| **对象池 + 纯数据组件（无类继承）** | 折中方案，但 Arcade 物理要求实体是 Sprite/Body，纯数据组件需手动同步 body，复杂化。**现阶段否决，留作 ECS 迁移中间态** |
